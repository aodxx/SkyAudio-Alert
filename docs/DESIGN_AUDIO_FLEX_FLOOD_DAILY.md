# Design Spec — รายงานน้ำท่วมรายวัน + พยากรณ์อากาศ

**โปรเจกต์:** SkyAudio-Alert — น้องจุ่นจ้าน  
**วันที่:** 2026-10-03  
**สถานะ:** Revised design direction สำหรับนำไป implement  
**ช่องทาง:** LINE Flex + LINE Audio Message ในกลุ่มบ้านลำพาย

---

## 1. เป้าหมายการออกแบบ

ออกแบบรายงานประจำวันที่:

- **เป็นกันเอง ฟังง่าย ไม่ตึงเครียด** แม้หัวข้อจะเป็นน้ำท่วม
- ให้ผู้ฟังรู้ก่อนว่า **ตอนนี้สถานการณ์เป็นอย่างไร และควรทำอะไร**
- ให้ **Gemini สร้างและเรียบเรียงเนื้อหาใหม่ตามข้อมูลสำคัญของวันนั้น** ไม่ใช้แบบฟอร์มรายงานตายตัว
- รองรับเสียง **หญิงและชาย** โดยเนื้อหาที่ Gemini สร้างจะถูกส่งเข้า Gemini TTS
- ทำ Flex ให้เป็น **การ์ดสั้น อ่านเร็ว ไม่กินพื้นที่หน้าแชทมากเกินไป**
- แบ่งข้อมูลเป็นกลุ่มชัดเจนด้วย **พื้นหลังไล่เฉดสี** ไม่ใช้เส้นและกล่องจำนวนมาก
- คงตัวตน **น้องจุ่นจ้าน** เป็นผู้รายงานประจำชุมชน
- มีปุ่มใหญ่ที่กดได้ทันทีสำหรับดูข้อมูลต้นทาง

หลักการ:

> จริงจังกับข้อเท็จจริง แต่เป็นมิตรกับคนฟัง — ไม่ใช้ภาษาข่มขู่ ไม่ทำให้ทุกฝนตกกลายเป็นภาวะวิกฤต

## 2. รายงานเสียงรายวัน

### 2.0 หลักการใหม่: เนื้อหาไม่ตายตัว

ระบบ **ไม่บังคับความยาว** และ **ไม่บังคับลำดับหัวข้อแบบตายตัว** อีกต่อไป Gemini จะตัดสินใจว่าแต่ละวันควรพูดอะไรและพูดมากน้อยเพียงใดจากข้อมูลที่ได้รับ เช่น:

- ถ้ามีถนนปิด/น้ำวิกฤต → พูดคำเตือนและการปฏิบัติตัวก่อน รายงานสั้นและตรงประเด็น
- ถ้าสถานการณ์ปกติและไม่มีเหตุสำคัญ → รายงานสั้นแบบเป็นกันเอง ไม่ยืดด้วยรายละเอียดที่ไม่จำเป็น
- ถ้ามีจุดวัดน้ำหลายจุดเปลี่ยนแปลง → เลือกเฉพาะจุดที่สำคัญต่อบ้านลำพาย
- ถ้าข้อมูลเก่าหรือยืนยันไม่ได้ → ใช้พื้นที่เสียงเพื่อบอกข้อจำกัดและชวนเปิดลิงก์ต้นทาง แทนการสรุปเกินข้อมูล

ยังคงมี **กฎความปลอดภัยที่ตายตัว** ซึ่ง Gemini ห้ามฝ่าฝืน:

1. ห้ามสร้างข้อเท็จจริง ตัวเลข เวลา จุดวัด ถนน หรือประกาศที่ไม่มีใน input
2. ห้ามเรียกฝนพยากรณ์ว่าเป็นน้ำท่วมจริง
3. `critical`, ถนนปิด หรือคำเตือนเร่งด่วนต้องมาก่อนข้อมูลรองอื่น
4. ต้องบอกเวลาอัปเดตเมื่อกล่าวถึงสถานการณ์น้ำ
5. ถ้า `unknown`/stale ต้องบอกว่ายังยืนยันล่าสุดไม่ได้
6. ห้ามพูดราคาปาล์ม ราคายาง หรือข่าวสารทั่วไป

ดังนั้น “ยืดหยุ่น” หมายถึงยืดหยุ่นด้านการเลือกประเด็น การเรียบเรียง น้ำเสียง และความยาว แต่ **ไม่ยืดหยุ่นด้านความจริงและข้อควรระวัง**

### 2.0.1 บทบาทของ Gemini Content Generation

เพิ่มชั้น `src/content/geminiReport.js` หรือชื่อเทียบเท่า ทำหน้าที่:

```text
normalized FloodSituation + WeatherAnalysis + location + date
    ↓
Gemini text generation
    ↓
validated ReportDraft { spokenText, shortSummary, actions, emphasis }
```

Gemini รับเฉพาะข้อมูล normalized ที่มาจาก adapter และกฎวิเคราะห์ ไม่ให้เรียกเว็บหรือค้นข้อมูลเองในขั้นสร้างเสียง ผลลัพธ์ควรบังคับเป็น structured JSON เพื่อให้ตรวจได้ก่อน TTS เช่น:

```json
{
  "spokenText": "...",
  "shortSummary": "เฝ้าระวังฝนช่วงเย็นและติดตามระดับน้ำ",
  "priority": "normal | watch | affected | critical | unknown",
  "actions": ["..."],
  "factsUsed": ["..."],
  "warnings": []
}
```

หลัง Gemini ตอบต้อง validate ว่า `spokenText` ไม่ว่าง, ไม่กล่าวข้อมูลนอก facts, ไม่กล่าว market/news, ไม่ขัดกับ `priority`, และมีข้อสงวนเมื่อ source stale/unknown ถ้า validation ไม่ผ่าน ให้ใช้ deterministic safety fallback ที่สั้นและไม่แต่งข้อมูลแทน ไม่ส่งข้อความที่ตรวจไม่ผ่านเข้า TTS

### 2.1 โปรไฟล์เสียง

ระบบรองรับ 2 โปรไฟล์ โดยใช้ `spokenText` ที่ Gemini สร้าง แล้วเปลี่ยนเฉพาะ voice/style configuration ของ Gemini TTS:

| โปรไฟล์ | ชื่อใน config | คาแรกเตอร์ | จังหวะ |
|---|---|---|---|
| **หญิง** | `female-friendly` | ผู้ประกาศชุมชนหญิง น้ำเสียงอบอุ่น สดใส สุภาพ เหมือนพี่สาวข้างบ้าน | ช้าเล็กน้อย เว้นจังหวะชัด ไม่แหลม ไม่เร่ง |
| **ชาย** | `male-friendly` | ผู้ประกาศชุมชนชาย เสียงนุ่ม มั่นใจ เป็นกันเอง เหมือนผู้ใหญ่บ้าน/ผู้ประกาศเสียงตามสายที่ใจเย็น | ปานกลางค่อนไปทางช้า เน้นคำเตือนด้วยเสียงนุ่ม ไม่ดุดัน |

**ค่าเริ่มต้น:** `male-friendly` ตามบุคลิกเดิมของน้องจุ่นจ้าน  
**การเปลี่ยนเสียง:** ใช้ `TTS_PROFILE=female-friendly` หรือ `TTS_PROFILE=male-friendly` โดยไม่แก้สคริปต์หรือ pipeline

หาก provider เสียงรองรับชื่อเสียงจริง ให้ map profile ไปยัง voice ที่กำหนดใน config เช่น `TTS_VOICE_NAME_FEMALE` และ `TTS_VOICE_NAME_MALE`; ห้าม hard-code ชื่อ voice ไว้ในตัวสร้างสคริปต์

### 2.2 Style prompt — หญิง

```text
Thai female community morning announcer, warm and friendly like a kind older sister
speaking to neighbors in a village LINE group. Calm, clear, reassuring and natural.
Not a news anchor, not dramatic, not alarmist. Speak Thai clearly for older listeners.
Use a relaxed conversational pace with short pauses between sections.
Give extra clarity to flood status, update time, actions and safety instructions.
Keep the mood friendly even when reporting a warning. Do not exaggerate or invent facts.
```

### 2.3 Style prompt — ชาย

```text
Thai male community morning announcer, warm, calm and familiar like a trusted village
speaker. Friendly and reassuring, not stern and not a television newsreader.
Speak Thai clearly for older listeners at a relaxed moderate-slow pace.
Use short natural pauses between flood status, actions and weather forecast.
Give clear but gentle emphasis to warning level, update time, roads and safety advice.
Keep the mood approachable. Do not exaggerate, do not sound urgent unless the data is critical,
and never invent a flood situation.
```

### 2.4 โครงสร้างคำสั่งสำหรับ Gemini TTS

ไม่กำหนด template หรือลำดับหัวข้อบังคับ Gemini TTS รับคำสั่งแบบแยก Director Instructions และ Spoken Text ตามหลักของ Gemini TTS:

```text
{English voice/style instructions}: {Thai spokenText generated and validated by Gemini}
```

`spokenText` ต้องเป็นภาษาไทยล้วนในส่วนที่ต้องพูด ส่วนคำสั่งสไตล์อยู่ก่อนเครื่องหมาย `:` และไม่ควรให้ Gemini TTS สร้างข้อเท็จจริงเพิ่มเอง

รูปแบบปัจจุบันใช้บทเสียง 4 ช่วงตาม Decision 025 ใน `DECISIONS.md` ไม่มีเป้าหมายนาทีตายตัว ให้เล่าข้อมูลจำเป็นอย่างเป็นธรรมชาติโดยไม่เติมคำซ้ำหรือยืดบท และใช้เพียง guard ทางเทคนิคจากความยาวไฟล์จริง 10 วินาที–5 นาที

### 2.5 กติกาการเขียนเสียง

- ใช้คำลงท้ายตาม profile: `ครับ` สำหรับชาย, `ค่ะ/นะคะ` สำหรับหญิง โดยไม่สลับในสคริปต์เดียว
- เปิดด้วยคำทักทาย ใช้ภาษาสนทนาแบบผู้ประกาศชุมชน มีสรุปสั้น ๆ ฝากความปรารถนาดี ขอบคุณผู้ฟัง บอกลา และกล่าวพบกันใหม่
- คำทักทาย คำเชื่อม คำขอบคุณ และคำอวยพรทั่วไปไม่จำเป็นต้องเป็น facts แต่ห้ามเพิ่มข้อกล่าวอ้าง คำแนะนำเฉพาะ ตัวเลข หรือเหตุการณ์ที่ไม่มีในข้อมูล
- ให้ Gemini เลือกจำนวนประโยคและจังหวะตามความสำคัญ ไม่เติมประโยคซ้ำเพื่อให้ถึงความยาวเป้าหมาย
- อ่าน **ระดับสถานการณ์ + เวลาอัปเดต** ก่อนรายละเอียดอื่นเมื่อมีความเสี่ยงหรือข้อมูลน้ำเป็นประเด็นหลัก
- ใช้ “มีรายงานว่า...” หรือ “ข้อมูลที่ระบบตรวจพบ...” แทนการฟันธง หาก confidence ต่ำ
- ถ้า `unknown` หรือ stale ให้พูดอย่างตรงไปตรงมา: “ขณะนี้ยังยืนยันสถานการณ์ล่าสุดไม่ได้”
- ถ้า `critical` หรือมีถนนปิด ให้พูดคำแนะนำความปลอดภัยก่อนพยากรณ์อากาศ
- ห้ามพูดราคาปาล์ม ราคายาง และข่าวสารทั่วไป
- ห้ามพูด URL ยาว ๆ; ให้บอกว่ากดปุ่มใน Flex เพื่อเปิดข้อมูล
- ไม่อ่านตัวเลขสถานีทุกจุดจนยาวเกินไป: เลือกจุดสำคัญสูงสุด 2–3 จุด
- ไม่ใช้คำว่า “ปลอดภัยแน่นอน” เพราะข้อมูลน้ำเปลี่ยนแปลงได้
- ใช้ `[short pause]` หรือ `[medium pause]` เฉพาะจุดที่ช่วยให้ฟังง่าย; ห้ามใส่ emotional adjective tag เช่น `[excited]` ใน spoken text

## 3. Flex Message — Compact Flood Card

### 3.1 ขนาดและพื้นที่

- ใช้ bubble เดียว `size: "kilo"` หรือ `mega` เฉพาะเมื่อข้อมูลจำเป็นมาก
- เป้าหมายความสูง: **ประมาณ 420–560 px** บนอุปกรณ์มือถือทั่วไป
- ไม่ใช้ภาพ header สูง 200px ในการ์ดหลัก เพราะเป็นสัดส่วนที่กินพื้นที่แชทมากเกินไป
- ใช้ header สี/ไล่เฉดแทนภาพเป็นค่าเริ่มต้น; ถ้าจะใช้ภาพหมู่บ้านให้ใช้ภาพขนาดเล็กไม่เกิน 72px หรือเป็น background ในช่วงหัวการ์ดเท่านั้น
- แสดงข้อมูลเฉพาะที่ช่วยตัดสินใจ ไม่แสดงรายการรายชั่วโมงยาว 8 ช่องใน Flex


### 3.3 กลุ่มเฉดสี

ใช้เฉดสีอ่อน-เข้มภายในกลุ่มเดียวกัน เพื่อให้แยกข้อมูลโดยไม่ต้องใส่กรอบซ้อนหลายชั้น

| กลุ่ม | สีเริ่มต้น | สีปลายทาง | ความหมาย |
|---|---|---|---|
| Identity | `#0B3954` | `#087E8B` | ตัวตน/ชื่อพื้นที่/วันที่ |
| Flood normal | `#0F766E` | `#2DD4BF` | ปกติ/ติดตามตามปกติ |
| Flood watch | `#155E75` | `#38BDF8` | เฝ้าระวัง |
| Flood affected | `#9A3412` | `#FB923C` | ได้รับผลกระทบ/เดินทางระวัง |
| Flood critical | `#991B1B` | `#F87171` | วิกฤต/ต้องทำตามคำเตือน |
| Flood unknown | `#334155` | `#94A3B8` | ยังยืนยันไม่ได้ |
| Weather | `#172554` | `#2563EB` | พยากรณ์อากาศ |
| Audio/footer | `#1E293B` | `#475569` | เชิญฟัง/ข้อมูลระบบ |

ใน LINE Flex หาก `linearGradient` มีข้อจำกัดกับ client รุ่นเก่า ให้ใช้ `backgroundColor` สีปลายทางเป็น fallback และคง contrast ของข้อความไว้

### 3.4 ข้อมูลที่แสดงในแต่ละกลุ่ม

**กลุ่ม A — Identity**

- `น้องจุ่นจ้าน`
- `บ้านลำพาย • พัทลุง`
- วันที่และเวลาออกประกาศ
- ไม่ใส่คำอธิบายยาวหรือภาพ header ขนาดใหญ่

**กลุ่ม B — Flood status**

- badge ระดับ: `ปกติ`, `เฝ้าระวัง`, `ได้รับผลกระทบ`, `วิกฤต`, `ยังยืนยันไม่ได้`
- เวลาอัปเดต
- แนวโน้มน้ำ: `เพิ่มขึ้น`, `ทรงตัว`, `ลดลง`
- จุด/ถนนสำคัญสูงสุด 1–2 รายการ
- คำแนะนำสั้น 1 บรรทัด
- ปุ่ม URI ขนาดใหญ่ 2 ปุ่ม

**กลุ่ม C — Weather**

- อุณหภูมิปัจจุบัน + ช่วงต่ำ/สูง
- สรุปฝนช่วงเวลาที่สำคัญเพียง 1 บรรทัด
- humidity/wind ใช้เป็น compact stats ไม่เกิน 3 ค่า
- ไม่ใส่ hourly cards หลายใบ

**กลุ่ม D — Audio/footer**

- `ฟังเสียงรายงานจากน้องจุ่นจ้าน`
- source สั้น ๆ เช่น `น้ำ: ศูนย์ข้อมูลพัทลุง • อากาศ: Open-Meteo`
- ไม่ใส่ URL ยาวในข้อความ

### 3.5 ปุ่มใหญ่

| Label | URI | สีปุ่ม |
|---|---|---|
| `ดูสถานะน้ำ / CCTV` | `https://cctv.maholan.net/` | `#0F766E` หรือสี flood ปัจจุบัน |
| `สถานการณ์น้ำพัทลุง` | `https://chachoengsao-flood.vercel.app/phatthalung` | `#1D4ED8` |
| `พยากรณ์อากาศ / เรดาร์ฝน` | `https://chachoengsao-flood.vercel.app/phatthalung/weather` | `#2563EB` |

ข้อกำหนด:

- ใช้ `action: { type: "uri", label, uri }`
- ความสูงปุ่มมาตรฐาน `48px` หรือค่า LINE ที่ใกล้เคียง
- เรียงแนวตั้งเพื่อให้กดง่ายบนมือถือ
- เว้นระยะระหว่างปุ่มอย่างน้อย `8px`
- ปุ่มต้องอยู่ในกลุ่ม Flood ไม่ซ่อนอยู่ท้ายการ์ด
- label สั้น ไม่ใช้คำว่า “คลิกที่นี่”
- ปุ่มพยากรณ์อากาศเป็นปุ่มที่ 3 แบบ optional/secondary; หากสถานการณ์น้ำอยู่ระดับ `affected` หรือ `critical` ให้คง 2 ปุ่มน้ำเป็นอันดับแรก และย้ายปุ่มอากาศไว้ใต้กลุ่ม Weather หรือซ่อนจาก compact variant หากพื้นที่ไม่พอ

## 4. กติกาไม่ให้ Flex กินพื้นที่แชท

1. ตัดภาพ header สูงออกจากการ์ดหลัก
2. จำกัดข้อมูลน้ำให้แสดงสูงสุด 2 จุด และใช้เสียง/ลิงก์สำหรับรายละเอียด
3. ไม่มี hourly forecast แบบหลายคอลัมน์ใน Flex ใหม่
4. ใช้ข้อความสรุป 1–2 บรรทัดต่อกลุ่ม
5. ไม่แสดง source URL เป็น raw text
6. ไม่แสดงข้อมูลที่ซ้ำกับเสียงโดยไม่ช่วยการตัดสินใจ
7. ใช้ separator น้อยที่สุด — ให้พื้นหลังไล่เฉดเป็นตัวแบ่งกลุ่ม
8. ถ้าสถานะปกติ ใช้กลุ่ม Flood ที่เตี้ยลง; ถ้าวิกฤตจึงขยายคำแนะนำเท่าที่จำเป็น
9. ใช้ `altText` สั้น เช่น `น้องจุ่นจ้านรายงานสถานการณ์น้ำพัทลุง: เฝ้าระวัง`
10. ตรวจภาพจริงบน LINE client อย่างน้อย 3 สถานะ: normal, watch, critical

---

## 5. Accessibility และ tone

- ข้อความหลักอย่างน้อย `sm`/`md`; สถานะใช้ `xl` หรือ `lg`
- contrast ของข้อความกับ gradient ต้องผ่านการตรวจด้วยภาพจริง
- อย่าใช้สีเพียงอย่างเดียว: ทุกระดับต้องมี label และ icon/ข้อความกำกับ
- ปุ่มต้องมี label ที่ผู้สูงอายุเข้าใจได้ทันที
- Flex ต้องยังเข้าใจได้แม้ไม่กดเสียง
- เสียงต้องยังฟังรู้เรื่องแม้ผู้ใช้ไม่เปิด Flex

## 6. สิ่งที่จะ implement ต่อ

### Audio

- เพิ่ม Gemini content-generation adapter และ structured output validation
- refactor `buildThaiScript()` ให้เป็นการเตรียม facts/context ไม่ใช่ template บังคับ
- ให้ Gemini เลือกประเด็น ลำดับ และความยาวตาม priority ของวันนั้น
- เพิ่ม safety fallback เมื่อ Gemini ตอบผิด schema, แต่งข้อเท็จจริง หรือ API ล้มเหลว
- เพิ่ม `TTS_PROFILE` และ mapping voice/style ชาย-หญิง
- ใช้ Gemini TTS เป็น provider หลัก โดย model เป็น config ไม่ hard-code รุ่นเดียว
- รองรับ model family ที่ทีมเลือกหลังตรวจ catalog/สิทธิ์จริง เช่น Gemini Flash TTS หรือ Flash-Lite TTS; ตัวอย่างชื่อใน config ต้อง verify กับ API ก่อน deploy
- เพิ่ม fixtures สำหรับ male/female และ unknown/stale/critical
- validate duration/encoding/ไฟล์จริงหลัง TTS โดยไม่มี target duration แบบตายตัว

### Flex

- เพิ่ม `floodStatusBlock()` และ `sourceButtonsBlock()`
- ปรับ `headerBlock()` เป็น compact identity strip
- เพิ่ม gradient group helpers พร้อม solid-color fallback
- เปลี่ยน builder เป็น flood-first และลด hourly section
- เพิ่ม test ตรวจ URI ปุ่ม, label, ขนาด, ลำดับกลุ่ม และ altText

### Configuration

```text
TTS_PROFILE=male-friendly
GEMINI_CONTENT_MODEL=
GEMINI_TTS_MODEL=
TTS_VOICE_NAME_MALE=
TTS_VOICE_NAME_FEMALE=
TTS_PROVIDER=gemini
FLEX_COMPACT=true
```

`GEMINI_CONTENT_MODEL` และ `GEMINI_TTS_MODEL` ต้องเลือกจาก model catalog/เอกสาร API ที่ใช้งานจริงในเวลาพัฒนา ไม่ควรสมมติว่า model example อย่าง `gemini-3.8-flash-tts` หรือชื่อ Flash-Lite TTS จะเปิดให้ใช้กับทุก key/ทุก endpoint

## 7. Definition of Done ด้าน design

- [ ] มีเสียงชายและหญิงที่โทนเป็นกันเอง ไม่ตึงเครียด
- [ ] Gemini สร้างเนื้อหาตาม facts ของแต่ละวันโดยไม่ใช้ template บังคับ
- [ ] ความยาวเสียงเปลี่ยนตาม priority/ข้อมูลสำคัญของวัน และไม่มี target duration ตายตัว
- [ ] สคริปต์ที่ผ่าน validation เปลี่ยน profile ได้โดยไม่แก้ logic ข้อมูล
- [ ] Gemini TTS model/voice ตั้งค่าผ่าน environment และตรวจ availability ก่อน deploy
- [ ] สถานการณ์น้ำอยู่ก่อนอากาศในเสียงและ Flex
- [ ] Flex มี 2 ปุ่มใหญ่ตาม URL ที่กำหนด
- [ ] Flex แบ่งกลุ่มด้วย gradient และมี fallback สีทึบ
- [ ] Flex ไม่มีภาพ header สูงที่กินพื้นที่มาก
- [ ] Flex แสดงข้อมูลสูงสุดที่จำเป็นและอ่านจบได้เร็ว
- [ ] มี test สำหรับ normal/watch/affected/critical/unknown
- [ ] ทดสอบภาพจริงบน LINE แล้วไม่เกิดข้อความล้นหรือปุ่มเล็กเกินไป
